# 02. FOLDER & PROJECT STRUCTURE

## Amaç

Bu doküman, Antrenova projesinin klasör yapısını, kaynak kod organizasyonunu ve geliştirme standartlarını tanımlar.

Doğru klasör yapısı yalnızca dosyaları düzenlemek için değildir. Kodun okunabilirliğini artırır, ekip çalışmasını kolaylaştırır, bakım maliyetini düşürür ve yeni geliştiricilerin projeye hızlı adapte olmasını sağlar.

Bu belge, projede geliştirilecek tüm modüller için zorunlu klasör standardını belirler.

---

# Tasarım Felsefesi

Proje yapısı;

- sade,
- tahmin edilebilir,
- modüler,
- ölçeklenebilir,
- tekrar etmeyen

bir yapıya sahip olmalıdır.

Bir geliştirici herhangi bir dosyanın nerede olması gerektiğini tahmin edebilmelidir.

---

# Temel Dizin Yapısı

Antrenova aşağıdaki ana dizin yapısını kullanmalıdır.

```text
app/
components/
features/
lib/
hooks/
providers/
services/
types/
schemas/
styles/
public/
docs/
supabase/
tests/
scripts/
```

Her dizinin sorumluluğu nettir.

---

# app/

Next.js App Router yapısını içerir.

Bu klasör;

- Route'lar
- Layout'lar
- Sayfalar
- Server Actions

için kullanılır.

İş kuralları burada bulunmamalıdır.

---

# components/

Tekrar kullanılabilir kullanıcı arayüzü bileşenlerini içerir.

Örneğin;

- Button
- Input
- Modal
- Dialog
- Card
- Table
- Badge
- Avatar

Component'ler mümkün olduğunca bağımsız olmalıdır.

---

# features/

İş modüllerinin bulunduğu ana klasördür.

Örneğin;

```text
features/

members/
finance/
attendance/
appointments/
packages/
crm/
dashboard/
settings/
notifications/
reports/
```

Her modül kendi içerisinde bağımsız çalışmalıdır.

---

# Feature Yapısı

Her modül aşağıdaki yapıyı takip etmelidir.

```text
members/

components/
services/
actions/
hooks/
schemas/
types/
utils/
```

Modül içerisindeki kod başka modüllerle karışmamalıdır.

---

# lib/

Platform genelinde kullanılan ortak yardımcı kodlar bulunur.

Örneğin;

- auth
- database
- logger
- cache
- permissions
- notifications
- validation

Bu klasör modülden bağımsızdır.

---

# services/

Harici servis bağlantıları burada bulunmalıdır.

Örneğin;

- WhatsApp
- SMTP
- SMS
- Storage
- AI
- Payment

Her servis tek sorumluluk ilkesine uygun geliştirilmelidir.

---

# providers/

React Provider yapıları burada bulunmalıdır.

Örneğin;

- Theme Provider
- Session Provider
- Query Provider

Provider'lar yalnızca uygulama seviyesinde kullanılmalıdır.

---

# hooks/

Tekrar kullanılabilir Custom Hook'lar burada yer almalıdır.

Örneğin;

- useAuth()
- useBusiness()
- usePermissions()
- usePagination()

Hook'lar yalnızca belirli bir amaca hizmet etmelidir.

---

# schemas/

Tüm doğrulama şemaları merkezi olarak yönetilmelidir.

Örneğin;

- Member Schema
- Finance Schema
- Login Schema

Doğrulama kuralları farklı dosyalarda tekrar edilmemelidir.

---

# types/

Ortak TypeScript tipleri burada bulunmalıdır.

Örneğin;

- User
- Business
- Member
- Trainer
- Payment

Tip tanımları tek bir kaynaktan yönetilmelidir.

---

# public/

Statik dosyalar.

Örneğin;

- Logo
- İkonlar
- Yazı Tipleri
- Görseller

Kod dosyaları burada bulunmamalıdır.

---

# docs/

Tüm proje dokümantasyonu burada yer almalıdır.

Önerilen yapı:

```text
docs/

uiux/
architecture/
business-rules/
database/
api/
workflow/
deployment/
```

Dokümanlar kodun ayrılmaz parçasıdır.

---

# tests/

Test dosyaları üretim kodundan ayrılmalıdır.

Örneğin;

- Unit Test
- Integration Test
- E2E Test

Her modül kendi testlerini içerebilir.

---

# scripts/

Tek seferlik veya yardımcı komut dosyaları burada tutulmalıdır.

Örneğin;

- Seed
- Migration
- Backup
- Import
- Export

---

# Dosya Adlandırma

Dosya isimleri tutarlı olmalıdır.

Örnekler:

```text
member-card.tsx
member-table.tsx
member-service.ts
member-schema.ts
member-actions.ts
```

Belirsiz isimlerden kaçınılmalıdır.

---

# İçe Aktarma Kuralları

Modüller mümkün olduğunca kendi içlerinden import yapmalıdır.

Katmanlar arasında doğrudan bağımlılık oluşturulmamalıdır.

Ortak kodlar yalnızca ortak klasörlerden kullanılmalıdır.

---

# Yasak Yapılar

Aşağıdaki durumlar önerilmez.

- Aynı yardımcı fonksiyonun farklı klasörlerde tekrar yazılması
- Bir modülün başka modülün private dosyalarını kullanması
- Belirsiz klasör isimleri
- Rastgele dosya yerleşimi

Klasör yapısı zamanla bozulmamalıdır.

---

# Ölçeklenebilirlik

Yeni modül eklendiğinde mevcut klasör yapısı değiştirilmemelidir.

Her yeni modül aynı standartları takip ederek sisteme eklenmelidir.

Bu yaklaşım uzun vadede bakım maliyetini önemli ölçüde azaltacaktır.

---

# Sonuç

Folder & Project Structure, Antrenova'nın kaynak kod organizasyonunun temelini oluşturur. Modüler klasör yapısı, ortak standartlar ve net sorumluluk ayrımı sayesinde proje büyüdükçe kod tabanı düzenini korur, ekip çalışmasını kolaylaştırır ve yeni özelliklerin güvenli şekilde geliştirilmesine olanak sağlar.
