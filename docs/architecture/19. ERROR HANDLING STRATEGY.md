# 19. ERROR HANDLING STRATEGY

## Amaç

Bu doküman, Antrenova platformunda hata yönetimi (Error Handling) stratejisini, hata sınıflandırmalarını, kullanıcıya gösterilecek mesaj standartlarını ve sistem genelinde uygulanacak hata yönetim prensiplerini tanımlar.

Hata yönetimi yalnızca oluşan hataları göstermek değildir. Amaç; kullanıcı deneyimini korumak, veri kaybını önlemek, geliştiricilere tanılama imkânı sunmak ve sistemin kararlılığını artırmaktır.

Bu belge, platform genelinde uygulanacak hata yönetim standartlarını belirler.

---

# Mimari Felsefesi

Hatalar;

- yönetilebilir,
- izlenebilir,
- kullanıcı dostu,
- geliştirici açısından analiz edilebilir

olmalıdır.

Hiçbir hata kullanıcıyı belirsizlik içerisinde bırakmamalıdır.

---

# Hata Sınıflandırması

Antrenova'da hatalar aşağıdaki gruplara ayrılmalıdır.

### Kullanıcı Hataları

Örneğin;

- Eksik bilgi girildi
- Geçersiz e-posta
- Yanlış şifre
- Zorunlu alan boş bırakıldı

Bu hatalar kullanıcı tarafından düzeltilebilir.

---

### Yetkilendirme Hataları

Örneğin;

- Yetkiniz bulunmuyor
- Bu şubeye erişemezsiniz
- Finans modülü erişimi yok

Bu hatalar güvenlik kaynaklıdır.

---

### İş Kuralı Hataları

Örneğin;

- Paket süresi dolmuş
- Aynı saatte başka randevu mevcut
- Üyenin aktif üyeliği bulunmuyor

Bu hatalar Domain katmanından gelir.

---

### Sistem Hataları

Örneğin;

- Veritabanı bağlantısı kesildi
- Storage servisi erişilemiyor
- Harici API cevap vermedi

Bu hatalar kullanıcıya teknik detay içermeden gösterilmelidir.

---

# Ortak Hata Formatı

Tüm API'ler aynı hata yapısını döndürmelidir.

```json
{
  "success": false,
  "code": "MEMBER_NOT_FOUND",
  "message": "Üye bulunamadı.",
  "details": []
}
```

Hata kodları benzersiz ve anlamlı olmalıdır.

---

# Kullanıcı Mesajları

Hata mesajları teknik terimler içermemelidir.

Yanlış örnek:

> SQL Error 23505

Doğru örnek:

> Aynı e-posta adresine sahip başka bir kullanıcı bulunmaktadır.

Mesajlar çözüm odaklı olmalıdır.

---

# Doğrulama Hataları

Form doğrulama hataları ilgili alanın yanında gösterilmelidir.

Kullanıcı tüm alanları tekrar incelemek zorunda kalmamalıdır.

İlk hatalı alana otomatik odaklanılmalıdır.

---

# Global Hata Sayfası

Beklenmeyen sistem hatalarında ortak hata ekranı kullanılmalıdır.

Ekranda aşağıdaki bilgiler yer almalıdır.

- Kullanıcı dostu açıklama
- Tekrar dene butonu
- Ana sayfaya dön
- Destek ile iletişime geç

Teknik detaylar gösterilmemelidir.

---

# Loglama

Tüm beklenmeyen hatalar merkezi log sistemine kaydedilmelidir.

Kayıtlar aşağıdaki bilgileri içermelidir.

- Tarih
- Kullanıcı
- business_id
- Modül
- Hata Kodu
- Stack Trace
- Tarayıcı Bilgisi

Bu bilgiler yalnızca geliştiriciler tarafından görüntülenebilmelidir.

---

# Retry Stratejisi

Geçici hatalarda sistem otomatik tekrar denemelidir.

Örneğin;

- Harici API
- Bildirim Gönderimi
- Dosya Yükleme

Kullanıcı aynı işlemi tekrar yapmak zorunda kalmamalıdır.

---

# Kritik Hatalar

Aşağıdaki durumlar kritik hata olarak değerlendirilmelidir.

- Veri bütünlüğü bozulması
- Finansal işlem başarısızlığı
- Güvenlik ihlali
- Authentication problemi

Bu olaylar anında yöneticilere bildirilebilmelidir.

---

# Audit Log

Kritik hata oluşturan işlemler Audit Log sistemine kaydedilmelidir.

Başarısız finans işlemleri, yetkisiz erişim denemeleri ve güvenlik ihlalleri ayrıca raporlanmalıdır.

---

# Kullanıcı Deneyimi

Bir hata oluştuğunda;

- Kullanıcının girdiği veriler mümkün olduğunca korunmalıdır.
- İşlem neden başarısız olduğu açıklanmalıdır.
- Tekrar deneme kolay olmalıdır.

Hata ekranları kullanıcıyı cezalandırmamalıdır.

---

# Monitoring

Hatalar merkezi izleme sisteminde takip edilmelidir.

Ölçülebilecek metrikler:

- Günlük hata sayısı
- Modül bazlı hata oranı
- Ortalama çözüm süresi
- En sık görülen hata kodları

Bu veriler sistem kalitesini artırmak için kullanılmalıdır.

---

# Güvenlik

Hata mesajlarında aşağıdaki bilgiler gösterilmemelidir.

- SQL sorguları
- Sunucu yolları
- API anahtarları
- Stack Trace
- Veritabanı yapısı

Teknik bilgiler yalnızca log sisteminde saklanmalıdır.

---

# Ölçeklenebilirlik

İlerleyen sürümlerde aşağıdaki özellikler eklenebilmelidir.

- Gerçek Zamanlı Hata Bildirimleri
- Sentry Benzeri İzleme Sistemleri
- Yapay Zekâ Destekli Hata Analizi
- Otomatik Hata Gruplandırma
- Performans Analizi

Mevcut hata yönetim yapısı değiştirilmeden genişleyebilmelidir.

---

# Değiştirilemez Kurallar

Aşağıdaki kurallar tüm platform için zorunludur.

- Ortak hata formatı kullanılacaktır.
- Teknik hata mesajları kullanıcıya gösterilmeyecektir.
- Kritik hatalar loglanacaktır.
- Audit Log entegrasyonu sağlanacaktır.
- business_id bilgisi korunacaktır.
- Kullanıcı verileri hata durumunda mümkün olduğunca kaybedilmeyecektir.

---

# Sonuç

Error Handling Strategy, Antrenova'nın hata yönetim yaklaşımını standartlaştırır. Kullanıcı dostu mesajlar, merkezi loglama, güvenli hata yönetimi ve güçlü izleme altyapısı sayesinde sistem hem son kullanıcılar hem de geliştiriciler için güvenilir, sürdürülebilir ve kolay yönetilebilir bir hata yönetim modeli sunar.
