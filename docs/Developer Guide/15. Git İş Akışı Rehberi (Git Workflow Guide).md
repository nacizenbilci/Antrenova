# 15. Git İş Akışı Rehberi (Git Workflow Guide)

> **Doküman Kodu:** DEV-15

> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** Deployment Standards, Code Review Guide, Coding Standards, Developer Guide Overview

---

# 1. Amaç

Bu dokümanın amacı, Antrenova projesinde kaynak kod yönetiminin ortak kurallarla yürütülmesini, Git geçmişinin okunabilir olmasını ve ekip içindeki geliştirme süreçlerinin güvenli şekilde ilerlemesini sağlamaktır.

Git yalnızca kod saklama aracı değildir. Kod geçmişini koruyan, ekip çalışmalarını yöneten, sürüm takibini kolaylaştıran ve güvenli yayın süreçlerini destekleyen temel geliştirme altyapısıdır.

Platformdaki tüm geliştiriciler bu iş akışına uygun çalışmalıdır.

---

# 2. Temel İlkeler

Git kullanımı aşağıdaki prensiplere uygun olmalıdır.

- Küçük değişiklikler yapılmalıdır.
- Anlamlı Commit oluşturulmalıdır.
- Geçmiş okunabilir olmalıdır.
- Kod incelemesi desteklenmelidir.
- Ana dal korunmalıdır.

Commit geçmişi proje geçmişidir.

---

# 3. Branch Yapısı

Standart Branch yapısı aşağıdaki gibidir.

```text
main

develop

feature/*

fix/*

hotfix/*

release/*
```

Her Branch belirli bir amaca hizmet etmelidir.

---

# 4. Feature Branch

Yeni geliştirmeler Feature Branch üzerinde yapılmalıdır.

Örneğin.

```text
feature/member-management

feature/payment-module

feature/dashboard-statistics
```

Bir Branch yalnızca tek geliştirmeyi içermelidir.

---

# 5. Fix Branch

Hata düzeltmeleri ayrı Branch üzerinde yapılmalıdır.

Örneğin.

```text
fix/login-error

fix/payment-validation

fix/member-filter
```

Hata düzeltmeleri yeni özelliklerle karıştırılmamalıdır.

---

# 6. Commit Mesajları

Commit mesajları kısa ve açıklayıcı olmalıdır.

Örneğin.

```text
feat: add member package management

fix: resolve payment calculation issue

refactor: simplify reservation service

docs: update api documentation
```

Belirsiz Commit mesajları kullanılmamalıdır.

---

# 7. Küçük Commitler

Büyük değişiklikler tek Commit halinde gönderilmemelidir.

Kurallar.

- Tek konu
- Küçük kapsam
- Kolay geri alma

Her Commit bağımsız değerlendirilebilmelidir.

---

# 8. Merge Süreci

Merge işlemleri kontrollü yapılmalıdır.

Merge öncesinde.

- Kod incelemesi
- Test
- Çakışma kontrolü

tamamlanmalıdır.

Doğrudan Main Branch'e Merge yapılmamalıdır.

---

# 9. Çakışmalar

Merge Conflict dikkatli çözülmelidir.

Kurallar.

- Manuel kontrol
- Test çalıştırma
- Gerektiğinde ikinci göz

Çakışmalar otomatik çözülmüş kabul edilmemelidir.

---

# 10. Release Branch

Yayın hazırlıkları Release Branch üzerinde yapılmalıdır.

İçerik.

- Son kontroller
- Sürüm numarası
- Testler
- Dokümantasyon

Release tamamlandıktan sonra Main'e aktarılmalıdır.

---

# 11. Hotfix

Production hataları Hotfix Branch ile çözülmelidir.

Örneğin.

```text
hotfix/login-security

hotfix/payment-service
```

Hotfix sonrasında Develop dalı da güncellenmelidir.

---

# 12. Git Ignore

Takip edilmemesi gereken dosyalar `.gitignore` içerisinde tanımlanmalıdır.

Örneğin.

- Environment dosyaları
- Build çıktıları
- Cache dosyaları
- IDE ayarları

Gizli bilgiler Git deposuna gönderilmemelidir.

---

# 13. Kod İnceleme

Merge öncesinde aşağıdaki konular değerlendirilmelidir.

- Kod kalitesi
- Test durumu
- Güvenlik
- Dokümantasyon
- Performans

Review süreci zorunlu olmalıdır.

---

# 14. Sürekli İyileştirme

Git iş akışı düzenli analiz edilmelidir.

İyileştirilebilecek alanlar.

- Branch yönetimi
- Commit kalitesi
- Merge süresi
- Kod inceleme süreci
- Release yönetimi

Ekip ihtiyaçlarına göre süreç geliştirilebilir.

---

# 15. Genel Kurallar

Git Workflow Guide, Antrenova projesindeki kaynak kod yönetiminin ortak standartlarını tanımlar. Tüm geliştirmeler uygun Branch yapısında yapılmalı, anlamlı Commit mesajları kullanılmalı, kod incelemesi tamamlanmadan Merge gerçekleştirilmemeli ve Main Branch her zaman yayınlanabilir durumda tutulmalıdır.

Bu yaklaşım sayesinde kod geçmişi düzenli kalır, ekip içi iş birliği kolaylaşır, sürüm yönetimi güvenli hale gelir ve platform uzun vadede sürdürülebilir bir geliştirme sürecine sahip olur.
