# 10. Hata Yönetimi Standartları (Error Handling Guide)

> **Doküman Kodu:** DEV-10  
> **Dosya Adı:** `10_ERROR_HANDLING_GUIDE.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Standards, Logging Standards, Monitoring & Observability, Coding Standards, Security Standards

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda oluşabilecek tüm hata durumlarının standart şekilde ele alınmasını, kullanıcı deneyiminin korunmasını ve geliştiricilerin ortak bir hata yönetim modeli kullanmasını sağlamaktır.

Hata yönetimi yalnızca `try/catch` bloklarından oluşmaz. Beklenen ve beklenmeyen hataların ayrıştırılması, loglanması, kullanıcıya uygun mesajların gösterilmesi, izleme sistemine aktarılması ve gerektiğinde otomatik aksiyon alınmasını kapsayan bütünsel bir süreçtir.

Platformdaki tüm uygulama katmanları bu standartlara uygun hata yönetimi uygulamalıdır.

---

# 2. Temel İlkeler

Hata yönetimi aşağıdaki prensiplere uygun olmalıdır.

- Tahmin edilebilir olmalıdır.
- Kullanıcı dostu olmalıdır.
- Loglanmalıdır.
- İzlenebilir olmalıdır.
- Güvenli olmalıdır.

Hiçbir hata sessiz şekilde geçiştirilmemelidir.

---

# 3. Hata Türleri

Platformdaki hatalar aşağıdaki gruplara ayrılmalıdır.

- Validation Errors
- Business Rule Errors
- Authorization Errors
- Infrastructure Errors
- Unexpected Errors

Her hata türü farklı şekilde ele alınmalıdır.

---

# 4. Validation Hataları

Kullanıcının hatalı veri girmesi sonucu oluşur.

Örneğin.

- Zorunlu alan eksik
- Hatalı e-posta
- Geçersiz tarih
- Negatif tutar

Bu hatalar kullanıcıya açık şekilde gösterilmelidir.

---

# 5. Business Rule Hataları

İş kurallarının ihlal edilmesi sonucu oluşur.

Örneğin.

- Paket süresi dolmuş
- Seans hakkı kalmamış
- Aynı saate ikinci rezervasyon
- Yetkisiz şube erişimi

Mesajlar iş kuralını açıklamalıdır.

---

# 6. Yetkilendirme Hataları

Yetki eksikliğinden kaynaklanan hatalar güvenli şekilde yönetilmelidir.

Örneğin.

- Giriş yapılmamış
- Yetki bulunmuyor
- Token süresi dolmuş

Sistem iç detayları kullanıcıya gösterilmemelidir.

---

# 7. Sunucu Hataları

Beklenmeyen sistem hataları kullanıcıya teknik detay vermemelidir.

Kullanıcı mesajı örneği.

```text
Beklenmeyen bir hata oluştu.
Lütfen daha sonra tekrar deneyiniz.
```

Teknik ayrıntılar yalnızca log sistemine yazılmalıdır.

---

# 8. Try/Catch Kullanımı

Hata yönetimi bilinçli yapılmalıdır.

Kurallar.

- Gerekli yerlerde kullanılmalıdır.
- Hatalar yeniden fırlatılabilir.
- Sessiz Catch bloklarından kaçınılmalıdır.

Boş Catch bloğu kullanılmamalıdır.

---

# 9. Loglama

Her kritik hata merkezi log sistemine gönderilmelidir.

Kaydedilecek bilgiler.

- Hata türü
- Servis
- Request ID
- Kullanıcı
- Business ID
- Stack Trace

Kişisel veriler loglanmamalıdır.

---

# 10. İzleme

Beklenmeyen hatalar Monitoring sistemine aktarılmalıdır.

Takip edilecek bilgiler.

- Hata sıklığı
- Tekrarlayan hatalar
- Servis bazlı dağılım
- Çözüm süresi

Kritik hatalar alarm üretmelidir.

---

# 11. API Hataları

API yanıtları standart hata yapısını kullanmalıdır.

İçerik.

- Error Code
- Message
- Details (gerekiyorsa)
- Request ID

Tüm endpoint'ler aynı hata formatını kullanmalıdır.

---

# 12. Kullanıcı Deneyimi

Hata oluştuğunda kullanıcı yönlendirilmelidir.

Örneğin.

- Yeniden dene
- Giriş yap
- Destek ile iletişime geç

Kullanıcı belirsizlik yaşamamalıdır.

---

# 13. Kod İnceleme

Kod incelemelerinde aşağıdaki konular kontrol edilmelidir.

- Sessiz hata var mı?
- Log oluşturulmuş mu?
- Kullanıcı mesajı uygun mu?
- Güvenlik korunmuş mu?

Hata yönetimi kod kalitesinin parçasıdır.

---

# 14. Sürekli İyileştirme

Hata kayıtları düzenli analiz edilmelidir.

İyileştirilebilecek alanlar.

- Tekrarlayan hatalar
- Kullanıcı deneyimi
- Log kalitesi
- Alarm doğruluğu
- Çözüm süresi

En sık oluşan hatalar öncelikli olarak iyileştirilmelidir.

---

# 15. Genel Kurallar

Error Handling Guide, Antrenova platformunda tüm hata durumlarının standart şekilde yönetilmesini sağlayan temel geliştirme kurallarını tanımlar. Hatalar türlerine göre sınıflandırılmalı, kullanıcıya anlaşılır mesajlar gösterilmeli, teknik detaylar güvenli şekilde loglanmalı ve tüm kritik olaylar izleme sistemine aktarılmalıdır.

Bu yaklaşım sayesinde kullanıcı deneyimi korunur, hata analizleri kolaylaşır, güvenlik riskleri azalır ve platform büyüdükçe sürdürülebilir bir hata yönetim altyapısı oluşturulur.
