# 03. Endpoint İsimlendirme Standartları (Endpoint Naming)

> **Doküman Kodu:** API-03  
> **Dosya Adı:** `03_ENDPOINT_NAMING.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Design Principles, REST API Standards, API Versioning, API Documentation

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda geliştirilecek tüm API endpoint'lerinin ortak isimlendirme kurallarını belirlemek ve platform genelinde tutarlı bir URL yapısı oluşturmaktır.

Doğru endpoint isimlendirmesi yalnızca okunabilirliği artırmaz; istemci geliştirmeyi kolaylaştırır, dokümantasyonu sadeleştirir ve yeni geliştiricilerin sistemi daha hızlı öğrenmesini sağlar. Aynı işlevi yerine getiren servislerin farklı isimlerle sunulması teknik borç oluşturur ve bakım maliyetini artırır.

Bu nedenle tüm endpoint'ler ortak standartlara uygun oluşturulmalıdır.

---

# 2. Temel İlkeler

Endpoint isimlendirmesi aşağıdaki kurallara uygun olmalıdır.

- İngilizce kullanılmalıdır.
- Küçük harf kullanılmalıdır.
- Çoğul (Plural) isimler tercih edilmelidir.
- Kaynak odaklı olmalıdır.
- İşlem isimleri URL içerisinde yer almamalıdır.
- Tutarlı yapı korunmalıdır.

Platform genelinde aynı sözlük kullanılmalıdır.

---

# 3. Kaynak İsimleri

Her endpoint bir iş nesnesini temsil etmelidir.

Örnekler.

```text
/api/v1/members
/api/v1/trainers
/api/v1/packages
/api/v1/payments
/api/v1/reservations
/api/v1/branches
```

Kaynak isimleri mümkün olduğunca kısa ve anlamlı olmalıdır.

---

# 4. Çoğul Kullanımı

Endpoint isimleri çoğul kullanılmalıdır.

Doğru örnekler.

```text
/members
/payments
/invoices
/notifications
```

Yanlış örnekler.

```text
/member
/payment
/invoice
```

Platform genelinde tek tip kullanım korunmalıdır.

---

# 5. İşlem İsimlerinden Kaçınma

URL içerisinde işlem adı kullanılmamalıdır.

Yanlış örnekler.

```text
/getMembers
/createMember
/deletePayment
/updateTrainer
```

Doğru yaklaşım.

```text
GET /members
POST /members
DELETE /payments/{id}
PATCH /trainers/{id}
```

İşlem HTTP metoduyla ifade edilmelidir.

---

# 6. Alt Kaynaklar

İlişkili veriler hiyerarşik yapı ile gösterilebilir.

Örnekler.

```text
/members/{id}/payments
/members/{id}/packages
/trainers/{id}/sessions
/packages/{id}/members
```

Gereksiz derin URL yapılarından kaçınılmalıdır.

---

# 7. Parametre Kullanımı

Kimlik bilgileri URL içerisinde path parametresi olarak verilmelidir.

Örneğin.

```text
/members/{memberId}
/payments/{paymentId}
```

Filtreleme amacıyla kimlik kullanılmamalıdır.

---

# 8. Filtreleme

Listeleme işlemlerinde filtreler Query String ile gönderilmelidir.

Örneğin.

```text
/members?status=active

/payments?date=2026-08

/reservations?trainer_id=...
```

Filtre bilgileri URL yoluna eklenmemelidir.

---

# 9. Arama

Arama işlemleri ayrı endpoint oluşturmak yerine Query Parametreleriyle yapılmalıdır.

Örneğin.

```text
/members?search=Ali

/trainers?search=Pilates
```

```text
/searchMembers
```

gibi özel endpoint'ler önerilmez.

---

# 10. Sıralama

Sıralama parametreleri Query String kullanmalıdır.

Örneğin.

```text
?sort=name

?sort=created_at

?order=desc
```

URL içerisinde sıralama bilgisi bulunmamalıdır.

---

# 11. Kısaltmalar

Genel kabul görmeyen kısaltmalar kullanılmamalıdır.

Yanlış.

```text
/mbr
/pay
/trn
```

Doğru.

```text
/members
/payments
/trainers
```

Endpoint ilk bakışta anlaşılmalıdır.

---

# 12. Tire ve Alt Çizgi

Endpoint isimlerinde boşluk kullanılmaz.

Kelime ayrımı gerektiğinde.

```text
kebab-case
```

tercih edilmelidir.

Örneğin.

```text
membership-types
payment-methods
attendance-reports
```

Snake Case kullanılmamalıdır.

---

# 13. Versiyonlama

Tüm endpoint'ler API sürüm numarası ile başlamalıdır.

Örneğin.

```text
/api/v1/members
/api/v1/payments
/api/v2/members
```

Versiyon numarası URL sonunda kullanılmamalıdır.

---

# 14. Dokümantasyon

Her endpoint aşağıdaki bilgilerle belgelenmelidir.

- URL
- HTTP Metodu
- Açıklama
- Parametreler
- Yetkilendirme
- Örnek istek
- Örnek cevap

Dokümantasyondaki URL ile gerçek endpoint birebir aynı olmalıdır.

---

# 15. Genel Kurallar

Endpoint isimlendirme standartları, Antrenova API mimarisinin okunabilirliğini ve sürdürülebilirliğini sağlayan temel kurallardan biridir. Tüm URL yapıları kaynak odaklı tasarlanmalı, REST prensiplerine uygun geliştirilmeli ve platform genelinde ortak isimlendirme sözlüğü kullanılmalıdır.

Bu nedenle yeni oluşturulan tüm endpoint'ler bu standartlara göre hazırlanmalı, mevcut isimlendirme yapısıyla uyumlu olmalı ve istemci uygulamalarının kolayca tahmin edebileceği tutarlı bir API tasarımı sunmalıdır.
