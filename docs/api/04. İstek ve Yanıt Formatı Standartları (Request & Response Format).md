# 04. İstek ve Yanıt Formatı Standartları (Request & Response Format)

> **Doküman Kodu:** API-04  
> **Dosya Adı:** `04_REQUEST_RESPONSE_FORMAT.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** REST API Standards, Endpoint Naming, Error Handling, API Documentation, API Security

---

# 1. Amaç

Bu dokümanın amacı, Antrenova API'lerinde kullanılacak istek (Request) ve yanıt (Response) formatlarını standartlaştırmak, istemci uygulamaları ile sunucu arasındaki veri alışverişini tutarlı ve öngörülebilir hale getirmektir.

Tüm API servisleri aynı veri yapısını kullanmalıdır. Bu sayede mobil uygulamalar, web paneli ve üçüncü taraf entegrasyonlar farklı endpoint'ler için özel ayrıştırma (parsing) kuralları yazmak zorunda kalmaz.

---

# 2. Temel İlkeler

Tüm API yanıtları aşağıdaki prensiplere uygun olmalıdır.

- JSON formatı kullanılmalıdır.
- Aynı yapı korunmalıdır.
- Gereksiz alan gönderilmemelidir.
- Yanıtlar okunabilir olmalıdır.
- Hata yapıları standart olmalıdır.

Platform genelinde tek Response sözlüğü kullanılmalıdır.

---

# 3. İçerik Türü

Tüm API servisleri aşağıdaki içerik tipini kullanmalıdır.

```http
Content-Type: application/json
```

İstemciler de aynı formatta veri göndermelidir.

Farklı veri tipleri yalnızca özel dosya yükleme işlemlerinde kullanılabilir.

---

# 4. Başarılı Yanıt Formatı

Başarılı tüm işlemler ortak Response yapısını kullanmalıdır.

Örnek.

```json
{
  "success": true,
  "message": "Operation completed successfully.",
  "data": {}
}
```

Alan isimleri değiştirilmemelidir.

---

# 5. Listeleme Yanıtı

Liste döndüren servislerde aşağıdaki yapı kullanılmalıdır.

```json
{
  "success": true,
  "data": [],
  "pagination": {}
}
```

Liste doğrudan kök seviyede döndürülmemelidir.

---

# 6. Tek Kayıt Yanıtı

Tek kayıt döndüren endpoint'ler aşağıdaki yapıyı kullanmalıdır.

```json
{
  "success": true,
  "data": {
    "id": "...",
    "name": "..."
  }
}
```

Ek alanlar yalnızca ihtiyaç halinde eklenmelidir.

---

# 7. Boş Sonuçlar

Kayıt bulunamadığında.

```json
{
  "success": true,
  "data": []
}
```

döndürülmelidir.

Boş liste hata olarak değerlendirilmemelidir.

---

# 8. Hata Yanıtı

Başarısız işlemlerde ortak hata yapısı kullanılmalıdır.

```json
{
  "success": false,
  "message": "Validation failed.",
  "errors": []
}
```

İç hata detayları son kullanıcıya gösterilmemelidir.

---

# 9. Validation Hataları

Alan doğrulama hataları aşağıdaki şekilde döndürülmelidir.

```json
{
  "success": false,
  "errors": [
    {
      "field": "email",
      "message": "Email is required."
    }
  ]
}
```

Her hata ilgili alanla ilişkilendirilmelidir.

---

# 10. Metadata

Gerektiğinde ek bilgiler aşağıdaki alanda gönderilebilir.

```json
{
  "meta": {}
}
```

Örneğin.

- İşlem süresi
- API sürümü
- Sunucu zamanı

Metadata isteğe bağlıdır.

---

# 11. Pagination Bilgisi

Liste endpoint'lerinde.

```json
{
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 250,
    "total_pages": 13
  }
}
```

alanı standart olarak kullanılmalıdır.

---

# 12. Null Kullanımı

Mümkün olduğunca boş string yerine NULL kullanılmalıdır.

Eksik alanlar Response'tan tamamen kaldırılmamalıdır.

İstemci her zaman aynı veri yapısını bekleyebilmelidir.

---

# 13. Tarih Formatı

Tüm tarih alanları ISO-8601 formatında döndürülmelidir.

Örneğin.

```text
2026-08-04T09:30:00Z
```

Yerel saat formatı API tarafından üretilmemelidir.

---

# 14. Dokümantasyon

Her endpoint için.

- Request örneği
- Response örneği
- Hata örneği
- Validation örneği

dokümantasyonda yer almalıdır.

Gerçek API davranışı ile örnekler aynı olmalıdır.

---

# 15. Genel Kurallar

İstek ve yanıt formatı standartları, Antrenova API'lerinin tutarlı ve kolay kullanılabilir olmasını sağlayan temel kurallardır. Tüm servisler ortak JSON yapısını kullanmalı, başarılı ve başarısız yanıtlar aynı sözlüğe uygun oluşturulmalı ve istemci uygulamalarının her endpoint için farklı veri yapılarıyla uğraşması engellenmelidir.

Bu nedenle Request & Response standartları platform genelinde değiştirilmeden uygulanmalı, yeni geliştirilen tüm servisler bu ortak veri modelini kullanmalı ve API dokümantasyonuyla tam uyumlu çalışmalıdır.
