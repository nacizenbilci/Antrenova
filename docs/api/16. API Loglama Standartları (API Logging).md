# 16. API Loglama Standartları (API Logging)

> **Doküman Kodu:** API-16  
> **Dosya Adı:** `16_API_LOGGING.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Security, Error Handling, Audit Rules, Database Security, Monitoring Standards

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda çalışan tüm API servislerinde uygulanacak loglama (Logging) standartlarını belirlemek, sistem davranışlarının izlenebilir olmasını sağlamak ve hata analizlerini kolaylaştırmaktır.

API logları yalnızca hata kayıtları değildir. Performans analizi, güvenlik olaylarının incelenmesi, kullanıcı işlemlerinin izlenmesi ve sistem sağlığının değerlendirilmesi için temel veri kaynağıdır. Ancak loglama yapılırken güvenlik ve kişisel veri koruma ilkeleri de gözetilmelidir.

---

# 2. Temel İlkeler

API loglama sistemi aşağıdaki prensiplere uygun olmalıdır.

- Tutarlı olmalıdır.
- Yapısal olmalıdır.
- Güvenli olmalıdır.
- Aranabilir olmalıdır.
- Performansı olumsuz etkilememelidir.

Her servis aynı log formatını kullanmalıdır.

---

# 3. Log Seviyeleri

Standart log seviyeleri aşağıdaki şekilde kullanılmalıdır.

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

Her olay uygun seviyede kayıt altına alınmalıdır.

---

# 4. Zorunlu Bilgiler

Her API logunda aşağıdaki bilgiler bulunmalıdır.

- Tarih ve saat
- HTTP metodu
- Endpoint
- Durum kodu
- İşlem süresi
- Kullanıcı kimliği (varsa)
- Business ID
- Request ID

Bu alanlar platform genelinde standarttır.

---

# 5. Request ID

Her API isteğine benzersiz bir Request ID atanmalıdır.

Bu kimlik sayesinde.

- istemci logları,
- sunucu logları,
- hata kayıtları

birbirleriyle ilişkilendirilebilir.

Request ID istemciye de döndürülebilir.

---

# 6. Performans Logları

Uzun süren API çağrıları ayrıca işaretlenmelidir.

Örneğin.

- 500 ms üzeri → Uyarı
- 1000 ms üzeri → Kritik inceleme

Eşik değerler sistem büyüklüğüne göre güncellenebilir.

---

# 7. Hata Logları

Beklenmeyen sistem hataları ayrıntılı şekilde kayıt altına alınmalıdır.

Loglarda bulunabilecek bilgiler.

- Hata türü
- Stack Trace
- İç servis adı
- SQL sorgusu (güvenliyse)

Bu bilgiler istemciye gönderilmemelidir.

---

# 8. Hassas Veriler

Aşağıdaki bilgiler loglara yazılmamalıdır.

- Şifre
- Access Token
- Refresh Token
- API Secret
- Kredi kartı bilgileri
- Kimlik numarası

Gerekli durumlarda maskeleme uygulanmalıdır.

---

# 9. Güvenlik Olayları

Aşağıdaki olaylar mutlaka kayıt altına alınmalıdır.

- Başarısız giriş denemeleri
- Yetki ihlalleri
- Rate Limit aşımı
- Şüpheli API kullanımı
- Token doğrulama hataları

Bu kayıtlar güvenlik analizlerinde kullanılmalıdır.

---

# 10. İşlem Süresi

Her API çağrısının çalışma süresi ölçülmelidir.

Bu bilgiler.

- performans analizi,
- kapasite planlaması,
- optimizasyon

için kullanılmalıdır.

---

# 11. Merkezi Loglama

Log kayıtları merkezi bir sistemde toplanmalıdır.

Örneğin.

- Elasticsearch
- Grafana Loki
- OpenSearch
- Cloud Logging

Dağıtık sistemlerde tek noktadan analiz yapılabilmelidir.

---

# 12. Saklama Süresi

Log kayıtları belirlenen politikaya göre saklanmalıdır.

Örneğin.

- Günlük loglar
- Aylık arşiv
- Güvenlik logları
- Hata logları

Eski kayıtlar güvenli şekilde arşivlenmelidir.

---

# 13. İzleme ve Uyarılar

Kritik log olayları otomatik uyarılar oluşturmalıdır.

Örneğin.

- Art arda 500 hataları
- Login saldırıları
- Performans düşüşü
- Veritabanı bağlantı sorunları

Operasyon ekibi hızlı bilgilendirilmelidir.

---

# 14. Dokümantasyon

Log formatı aşağıdaki bilgileri içermelidir.

- Alan açıklamaları
- Log seviyeleri
- Örnek kayıtlar
- Saklama politikası
- Güvenlik kuralları

Tüm servisler aynı log standardını kullanmalıdır.

---

# 15. Genel Kurallar

API loglama standartları, Antrenova platformunun güvenliği, performansı ve sürdürülebilirliği açısından kritik öneme sahiptir. Her API çağrısı ortak log yapısıyla kayıt altına alınmalı, hassas bilgiler korunmalı ve kritik olaylar merkezi izleme sistemleri üzerinden analiz edilebilmelidir.

Bu nedenle Logging altyapısı geliştirme sürecinin ayrılmaz bir parçası olmalı, tüm servislerde standartlaştırılmalı ve sistem büyüdükçe performans ile güvenlik analizlerini destekleyecek şekilde sürekli geliştirilmelidir.
