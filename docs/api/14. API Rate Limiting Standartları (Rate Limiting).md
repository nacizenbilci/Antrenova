# 14. API Rate Limiting Standartları (Rate Limiting)

> **Doküman Kodu:** API-14  
> **Dosya Adı:** `14_RATE_LIMITING.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Security, Authentication API, REST API Standards, API Logging, Database Performance

---

# 1. Amaç

Bu dokümanın amacı, Antrenova API'lerinin kötüye kullanımını önlemek, sistem kaynaklarını korumak ve tüm istemcilere adil erişim sağlamak amacıyla uygulanacak Rate Limiting standartlarını belirlemektir.

Rate Limiting yalnızca saldırıları engellemek için değil; hatalı çalışan istemcilerin sistemi aşırı yüklemesini önlemek, kaynak tüketimini dengelemek ve yüksek kullanıcı sayılarında hizmet kalitesini korumak için de gereklidir.

Platform genelindeki tüm API servisleri ortak Rate Limiting politikalarına uymalıdır.

---

# 2. Temel İlkeler

Rate Limiting sistemi aşağıdaki prensiplere uygun olmalıdır.

- Adil olmalıdır.
- Esnek olmalıdır.
- Ölçeklenebilir olmalıdır.
- İzlenebilir olmalıdır.
- Güvenli olmalıdır.

Kullanıcı deneyimini gereksiz yere olumsuz etkilememelidir.

---

# 3. Limit Türleri

Rate Limiting aşağıdaki kriterlere göre uygulanabilir.

- Kullanıcı bazlı
- IP bazlı
- API anahtarı bazlı
- Tenant bazlı
- Endpoint bazlı

Farklı servisler farklı limitlere sahip olabilir.

---

# 4. Varsayılan Limitler

Platform için örnek varsayılan limitler.

- Genel API → Dakikada 120 istek
- Login → Dakikada 10 istek
- Dosya yükleme → Dakikada 20 istek
- Webhook → Servis bazlı

Gerçek değerler operasyonel ihtiyaçlara göre güncellenebilir.

---

# 5. Kritik Endpoint'ler

Aşağıdaki endpoint'lerde daha sıkı limitler uygulanmalıdır.

- Login
- Şifre sıfırlama
- OTP doğrulama
- Token yenileme

Brute Force saldırıları önlenmelidir.

---

# 6. HTTP Yanıtı

Limit aşıldığında.

```http
429 Too Many Requests
```

döndürülmelidir.

Yanıt içerisinde bekleme süresi belirtilebilir.

---

# 7. Response Header

Aşağıdaki bilgiler Header üzerinden gönderilebilir.

```text
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

İstemciler kendi kullanım durumlarını takip edebilmelidir.

---

# 8. Kimlik Doğrulama Öncesi

Authentication gerektirmeyen endpoint'lerde IP tabanlı limit uygulanmalıdır.

Kimlik doğrulaması sonrasında kullanıcı bazlı limitlere geçilebilir.

Anonim istekler daha sıkı kontrol edilmelidir.

---

# 9. Tenant Bazlı Limit

Çok büyük işletmeler için tenant bazlı limitler uygulanabilir.

Örneğin.

- API kullanım kotası
- Lisans bazlı limit
- Paket bazlı limit

Bu yapı lisans modeliyle entegre çalışabilir.

---

# 10. İstisnalar

Bazı servisler Rate Limiting dışında tutulabilir.

Örneğin.

- Sistem içi servisler
- Güvenilir entegrasyonlar
- Yönetim servisleri

Bu istisnalar açık şekilde belgelenmelidir.

---

# 11. Performans

Rate Limiting sistemi API performansını önemli ölçüde düşürmemelidir.

Hızlı çalışan.

- Bellek tabanlı
- Dağıtık
- Cache destekli

çözümler tercih edilmelidir.

---

# 12. Loglama

Limit aşımı durumları kayıt altına alınmalıdır.

Kayıt bilgileri.

- Kullanıcı
- IP
- Endpoint
- Tarih
- Limit bilgisi

Aşırı kullanım davranışları analiz edilmelidir.

---

# 13. Güvenlik

Rate Limiting tek başına güvenlik çözümü değildir.

Aşağıdaki yapılarla birlikte kullanılmalıdır.

- Authentication
- Authorization
- WAF
- CAPTCHA
- Audit

Katmanlı güvenlik yaklaşımı uygulanmalıdır.

---

# 14. Dokümantasyon

API dokümantasyonunda aşağıdaki bilgiler belirtilmelidir.

- Limit politikası
- Hangi endpoint'lerde uygulandığı
- 429 hata örnekleri
- Header açıklamaları

İstemci geliştiricileri kullanım sınırlarını önceden bilmelidir.

---

# 15. Genel Kurallar

Rate Limiting, Antrenova API altyapısının güvenilirliğini ve sürdürülebilir performansını koruyan temel mekanizmalardan biridir. Tüm istemciler belirlenen kullanım sınırlarına uymalı, kritik endpoint'ler ek koruma altında olmalı ve limit aşımı durumları standart HTTP cevaplarıyla yönetilmelidir.

Bu nedenle Rate Limiting politikaları merkezi olarak yönetilmeli, sistem büyüdükçe yeniden değerlendirilmeli ve güvenlik ile performans hedeflerini birlikte destekleyecek şekilde sürekli optimize edilmelidir.
