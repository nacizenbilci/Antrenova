# 07. API Kimlik Doğrulama Standartları (Authentication API)

> **Doküman Kodu:** API-07  
> **Dosya Adı:** `07_AUTHENTICATION_API.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Security, Authorization API, REST API Standards, Multi-Tenant Database, Authentication Rules

---

# 1. Amaç

Bu dokümanın amacı, Antrenova API'lerinde kullanılacak kimlik doğrulama (Authentication) standartlarını belirlemek ve tüm istemcilerin güvenli şekilde sisteme erişmesini sağlamaktır.

Kimlik doğrulama, API güvenliğinin ilk katmanıdır. Kullanıcının kim olduğunu doğrulamadan hiçbir işletme verisine erişim sağlanmamalı ve hiçbir işlem gerçekleştirilmemelidir. Tüm istemci uygulamaları aynı doğrulama mekanizmasını kullanmalıdır.

---

# 2. Temel İlkeler

Kimlik doğrulama sistemi aşağıdaki prensiplere uygun olmalıdır.

- Güvenli olmalıdır.
- Stateless çalışmalıdır.
- Ölçeklenebilir olmalıdır.
- Multi-Tenant mimariyi desteklemelidir.
- Standart HTTP başlıklarını kullanmalıdır.

Kimlik doğrulama ile yetkilendirme birbirinden ayrı değerlendirilmelidir.

---

# 3. Token Tabanlı Yapı

Antrenova API'leri Token tabanlı kimlik doğrulama kullanacaktır.

İstemci giriş yaptıktan sonra.

- Access Token
- Gerekiyorsa Refresh Token

almalıdır.

Sunucu oturum (Session) bilgisi tutmamalıdır.

---

# 4. Authorization Header

Tüm korunan endpoint'lerde Token aşağıdaki standartla gönderilmelidir.

```http
Authorization: Bearer <token>
```

Token Query String veya Request Body içerisinde gönderilmemelidir.

---

# 5. Login İşlemi

Başarılı giriş sonrasında istemciye aşağıdaki bilgiler döndürülmelidir.

- Access Token
- Token süresi
- Kullanıcı bilgileri
- Business bilgisi
- Rol bilgisi

Şifre hiçbir zaman Response içerisinde yer almamalıdır.

---

# 6. Token Doğrulama

Her API isteğinde aşağıdaki kontroller yapılmalıdır.

- Token mevcut mu?
- Token geçerli mi?
- Süresi dolmuş mu?
- İmza doğrulandı mı?
- İptal edilmiş mi?

Doğrulama başarısızsa istek reddedilmelidir.

---

# 7. Token Süresi

Access Token sınırlı süre geçerli olmalıdır.

Süresi dolan Token ile işlem yapılamamalıdır.

Uzun ömürlü erişim yalnızca Refresh Token mekanizmasıyla sağlanmalıdır.

---

# 8. Logout

Çıkış işlemi sırasında.

- Token geçersiz hale getirilmeli,
- istemci tarafındaki bilgiler temizlenmeli,
- gerekiyorsa Refresh Token iptal edilmelidir.

Logout yalnızca istemci tarafında veri silmekten ibaret olmamalıdır.

---

# 9. Çoklu Cihaz

Bir kullanıcı aynı anda birden fazla cihazdan giriş yapabilir.

Her oturum bağımsız yönetilmelidir.

İstenirse kullanıcı tüm oturumlarını sonlandırabilmelidir.

---

# 10. Multi-Tenant Kontrolü

Kimlik doğrulama sonrasında.

- Business ID
- Branch ID
- Kullanıcı Rolü

belirlenmelidir.

Doğrulanan kullanıcı yalnızca kendi tenant verilerine erişebilmelidir.

---

# 11. Başarısız Girişler

Arka arkaya başarısız giriş denemeleri takip edilmelidir.

Belirlenen eşik aşıldığında.

- geçici engelleme,
- ek doğrulama,
- güvenlik bildirimi

uygulanabilir.

Brute Force saldırıları önlenmelidir.

---

# 12. Güvenlik

Kimlik doğrulama sırasında aşağıdaki bilgiler loglanmamalıdır.

- Şifre
- Token
- Gizli anahtar
- Tek kullanımlık kodlar

Log kayıtlarında hassas bilgiler maskelenmelidir.

---

# 13. Audit

Aşağıdaki işlemler Audit sistemine kaydedilmelidir.

- Başarılı giriş
- Başarısız giriş
- Çıkış
- Token iptali
- Şifre değişikliği

Güvenlik olayları izlenebilir olmalıdır.

---

# 14. Dokümantasyon

Authentication API aşağıdaki bilgileri içermelidir.

- Login Endpoint'i
- Logout Endpoint'i
- Header yapısı
- Token formatı
- Hata kodları
- Örnek istek ve cevaplar

Dokümantasyon istemci geliştiricileri için yeterli ayrıntıya sahip olmalıdır.

---

# 15. Genel Kurallar

Authentication API, Antrenova platformunun tüm güvenlik yapısının başlangıç noktasıdır. Her kullanıcı güvenli şekilde doğrulanmalı, Token tabanlı stateless mimari kullanılmalı ve tüm erişimler standart Authorization Header üzerinden gerçekleştirilmelidir.

Bu nedenle kimlik doğrulama süreçleri platform genelinde tek tip uygulanmalı, Multi-Tenant mimariyle tam uyumlu çalışmalı ve tüm güvenlik olayları Audit sistemi tarafından izlenebilir olmalıdır.
