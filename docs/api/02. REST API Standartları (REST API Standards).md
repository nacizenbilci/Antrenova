# 02. REST API Standartları (REST API Standards)

> **Doküman Kodu:** API-02  
> **Dosya Adı:** `02_REST_API_STANDARDS.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Design Principles, Endpoint Naming, Request Response Format, API Security, API Documentation

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda geliştirilecek tüm servislerin REST mimarisine uygun şekilde tasarlanmasını sağlayacak standartları belirlemektir.

REST (Representational State Transfer), API tasarımında yaygın olarak kullanılan mimari yaklaşımdır. Doğru uygulandığında API'lerin okunabilirliğini artırır, istemci geliştirmeyi kolaylaştırır, bakım maliyetini azaltır ve gelecekte yapılacak genişletmeleri destekler.

Platform genelindeki tüm HTTP servisleri bu standartlara uygun geliştirilmelidir.

---

# 2. Temel İlkeler

REST API tasarımında aşağıdaki prensipler uygulanmalıdır.

- Kaynak (Resource) odaklı tasarım
- Standart HTTP metotları
- Stateless iletişim
- Tek tip veri formatı
- Tahmin edilebilir URL yapısı
- Tutarlı hata yönetimi

Her endpoint aynı davranış modelini kullanmalıdır.

---

# 3. Kaynak Yapısı

Her endpoint bir kaynağı temsil etmelidir.

Örnekler.

```text
/api/v1/members
/api/v1/trainers
/api/v1/packages
/api/v1/payments
/api/v1/reservations
```

URL içerisinde işlem isimleri kullanılmamalıdır.

---

# 4. HTTP GET

GET yalnızca veri okumak amacıyla kullanılmalıdır.

Örnekler.

```http
GET /members

GET /members/{id}

GET /payments
```

GET isteği hiçbir veriyi değiştirmemelidir.

---

# 5. HTTP POST

POST yeni kayıt oluşturmak amacıyla kullanılmalıdır.

Örnekler.

```http
POST /members

POST /payments

POST /reservations
```

POST aynı isteğin tekrar gönderilmesi durumunda dikkatli yönetilmelidir.

---

# 6. HTTP PUT

PUT mevcut kaydı tamamen güncellemek için kullanılmalıdır.

İstemci tüm güncel alanları göndermelidir.

Örnek.

```http
PUT /members/{id}
```

Eksik alanlar silinmiş kabul edilmemelidir.

---

# 7. HTTP PATCH

PATCH yalnızca değişen alanları güncellemek amacıyla kullanılmalıdır.

Örneğin.

```http
PATCH /members/{id}
```

Sadece telefon numarası güncellenecekse diğer alanlar tekrar gönderilmemelidir.

---

# 8. HTTP DELETE

DELETE işlemi kayıt silme amacıyla kullanılmalıdır.

Antrenova'da varsayılan yaklaşım Soft Delete olduğundan.

```http
DELETE /members/{id}
```

isteği fiziksel silme yerine Soft Delete işlemi gerçekleştirebilir.

---

# 9. URL Yapısı

URL'ler kısa, anlaşılır ve çoğul isimlerle oluşturulmalıdır.

Doğru örnekler.

```text
/members

/trainers

/packages
```

Yanlış örnekler.

```text
/getMemberList

/createPayment

/memberOperations
```

---

# 10. Alt Kaynaklar

İlişkili kaynaklar hiyerarşik olarak gösterilebilir.

Örneğin.

```text
/members/{id}/payments

/members/{id}/reservations
```

Bu yapı gereksiz derinliğe ulaştırılmamalıdır.

---

# 11. İstek Gövdesi

GET ve DELETE isteklerinde Body kullanılmamalıdır.

POST, PUT ve PATCH işlemlerinde JSON formatı tercih edilmelidir.

İstemci yalnızca gerekli alanları göndermelidir.

---

# 12. Durum Kodları

REST servisleri standart HTTP durum kodlarını kullanmalıdır.

Örneğin.

```text
200 OK

201 Created

204 No Content

400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

500 Internal Server Error
```

Özel durum kodları oluşturulmamalıdır.

---

# 13. Güvenlik

REST API'ler aşağıdaki güvenlik katmanlarını desteklemelidir.

- Authentication
- Authorization
- HTTPS
- Rate Limiting
- Input Validation

Kimlik doğrulaması yapılmadan veri döndürülmemelidir.

---

# 14. Dokümantasyon

Her REST endpoint'i aşağıdaki bilgilerle belgelenmelidir.

- URL
- HTTP Metodu
- Parametreler
- Request Body
- Response Body
- Hata Kodları
- Yetki Gereksinimi

Dokümantasyon ile gerçek API davranışı uyumlu olmalıdır.

---

# 15. Genel Kurallar

REST API standartları, Antrenova platformundaki tüm servislerin ortak iletişim dilini oluşturur. Kaynak odaklı URL yapısı, standart HTTP metotları, JSON veri formatı ve tutarlı durum kodları kullanılarak geliştirilen servisler hem istemci uygulamaları hem de üçüncü taraf entegrasyonları için öngörülebilir ve sürdürülebilir bir yapı sağlar.

Bu nedenle tüm yeni API'ler REST prensiplerine uygun geliştirilmeli, mevcut standartlardan sapılmamalı ve platform genelinde tek tip iletişim modeli korunmalıdır.
