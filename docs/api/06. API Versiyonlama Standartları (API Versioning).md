# 06. API Versiyonlama Standartları (API Versioning)

> **Doküman Kodu:** API-06  
> **Dosya Adı:** `06_API_VERSIONING.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** API Design Principles, REST API Standards, Endpoint Naming, API Change Management, API Documentation

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda geliştirilecek tüm API servislerinin sürüm (Version) yönetimine ilişkin standartları belirlemek ve istemci uygulamalarının geriye dönük uyumluluğunu korumaktır.

API'ler zaman içerisinde yeni özellikler kazanacak, bazı alanlar değişecek ve yeni iş kuralları eklenecektir. Doğru versiyonlama stratejisi sayesinde eski istemciler çalışmaya devam ederken yeni istemciler de geliştirilmiş servislerden yararlanabilir.

Platform genelinde tek bir versiyonlama modeli kullanılmalıdır.

---

# 2. Temel İlkeler

API versiyonlama aşağıdaki prensiplere uygun olmalıdır.

- Geriye dönük uyumluluk korunmalıdır.
- Kırıcı değişiklikler yeni sürümde yapılmalıdır.
- Eski sürümler belirli süre desteklenmelidir.
- Sürüm bilgisi açık olmalıdır.
- Dokümantasyon her sürüm için ayrı tutulmalıdır.

Her istemci kullandığı API sürümünü açıkça bilmelidir.

---

# 3. URL Tabanlı Versiyonlama

Antrenova'da standart yaklaşım URL tabanlı versiyonlamadır.

Örnek.

```text
/api/v1/members
/api/v1/payments
/api/v1/trainers
```

Yeni büyük sürüm.

```text
/api/v2/members
```

şeklinde oluşturulmalıdır.

---

# 4. İlk Sürüm

Platformun ilk resmi sürümü.

```text
v1
```

olarak yayınlanacaktır.

Tüm istemci uygulamaları varsayılan olarak bu sürümü kullanacaktır.

`v0`, `beta` veya benzeri isimlendirmeler üretim ortamında kullanılmamalıdır.

---

# 5. Kırıcı Değişiklikler

Aşağıdaki değişiklikler yeni ana sürüm gerektirir.

- Endpoint kaldırılması
- Response yapısının değişmesi
- Request alanlarının kaldırılması
- URL değişikliği
- Kimlik doğrulama yönteminin değişmesi

Eski istemciler etkilenmemelidir.

---

# 6. Kırıcı Olmayan Değişiklikler

Aşağıdaki değişiklikler mevcut sürüm içerisinde yapılabilir.

- Yeni isteğe bağlı alan eklenmesi
- Yeni endpoint eklenmesi
- Performans iyileştirmeleri
- Güvenlik geliştirmeleri
- Dokümantasyon güncellemeleri

Mevcut istemciler çalışmaya devam etmelidir.

---

# 7. Sürüm Ömrü

Her API sürümü belirli bir yaşam döngüsüne sahip olmalıdır.

Önerilen aşamalar.

- Active
- Maintenance
- Deprecated
- Removed

Kullanımdan kaldırılacak sürümler önceden duyurulmalıdır.

---

# 8. Deprecated Süreci

Eski sürüm kaldırılmadan önce.

- geliştiriciler bilgilendirilmeli,
- geçiş rehberi hazırlanmalı,
- yeni sürüm önerilmelidir.

Ani sürüm kaldırmaları yapılmamalıdır.

---

# 9. Dokümantasyon

Her API sürümünün ayrı dokümantasyonu bulunmalıdır.

Dokümanlarda.

- Destek durumu
- Değişiklik listesi
- Yeni özellikler
- Geçiş notları

yer almalıdır.

Dokümantasyon sürümlerle birlikte güncellenmelidir.

---

# 10. Mobil Uygulamalar

Mobil uygulamalar eski API sürümlerini bir süre daha kullanabilir.

Bu nedenle.

- Geriye dönük uyumluluk
- Geçiş planı
- Kademeli güncelleme

desteklenmelidir.

Eski uygulamalar aniden çalışmaz hale getirilmemelidir.

---

# 11. Web Paneli

Web paneli mümkün olduğunca güncel API sürümünü kullanmalıdır.

Yeni özellikler yalnızca desteklenen sürümlerde geliştirilmelidir.

Eski sürümler gereksiz yere uzatılmamalıdır.

---

# 12. Test Süreci

Yeni API sürümü yayınlanmadan önce.

- Birim testleri
- Entegrasyon testleri
- Geriye dönük uyumluluk testleri

tamamlanmalıdır.

Eski sürümle karşılaştırmalı testler yapılmalıdır.

---

# 13. İzleme

API kullanım istatistikleri sürüm bazında takip edilmelidir.

Örneğin.

- En çok kullanılan sürüm
- Eski sürüm kullanıcıları
- Hata oranları
- Performans karşılaştırmaları

Bu bilgiler sürüm planlamasında kullanılmalıdır.

---

# 14. Geçiş Politikası

Yeni ana sürüme geçiş kontrollü şekilde yapılmalıdır.

Geçiş sürecinde.

- Duyurular
- Geçiş rehberi
- Örnek kodlar
- Destek süreci

hazırlanmalıdır.

İstemci geliştiricileri yalnız bırakılmamalıdır.

---

# 15. Genel Kurallar

API versiyonlama, Antrenova platformunun uzun yıllar boyunca kesintisiz geliştirilebilmesini sağlayan temel mimari standartlardan biridir. Her kırıcı değişiklik yeni bir ana sürümde yayınlanmalı, eski sürümler belirli süre desteklenmeli ve istemci uygulamalarının geçiş yapabilmesi için yeterli zaman tanınmalıdır.

Bu nedenle tüm API servisleri ortak versiyonlama politikasını kullanmalı, dokümantasyon sürümlerle birlikte güncellenmeli ve platform genelinde geriye dönük uyumluluk mümkün olan en yüksek seviyede korunmalıdır.
