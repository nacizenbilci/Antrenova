# 03. Git ve Branch Yönetimi Standartları (Git & Branch Strategy)

> **Doküman Kodu:** DEVOPS-03  
> **Dosya Adı:** `03_GIT_BRANCH_STRATEGY.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** Deployment Principles, CI/CD Standards, Code Review Standards, Software Architecture

---

# 1. Amaç

Bu dokümanın amacı, Antrenova projesinde kullanılacak Git sürüm kontrol sistemi ve Branch (dal) yönetimi standartlarını belirlemek, ekip çalışmasını kolaylaştırmak ve kod kalitesini korumaktır.

Git stratejisi yalnızca kod saklamak için kullanılmaz. Geliştirme sürecinin izlenmesi, değişikliklerin kontrol edilmesi, güvenli sürüm yayınlanması, geri dönüş yapılabilmesi ve ekip üyeleri arasında tutarlı çalışma düzeninin sağlanması için temel altyapıdır.

Projedeki tüm geliştiriciler aynı Git kurallarını uygulamalıdır.

---

# 2. Temel İlkeler

Git yönetimi aşağıdaki prensiplere uygun olmalıdır.

- İzlenebilir olmalıdır.
- Küçük değişikliklerle ilerlenmelidir.
- Geri alınabilir olmalıdır.
- Kod incelemesini desteklemelidir.
- Branch yapısı standart olmalıdır.

Ana dal doğrudan geliştirme amacıyla kullanılmamalıdır.

---

# 3. Ana Branch'ler

Projede aşağıdaki temel branch yapısı kullanılmalıdır.

```text
main
develop
```

Kurallar.

- `main` → Canlıya çıkan kararlı sürümler
- `develop` → Güncel geliştirme dalı

Bu iki dal korunmalıdır.

---

# 4. Feature Branch

Her yeni geliştirme ayrı Feature Branch üzerinde yapılmalıdır.

Adlandırma standardı.

```text
feature/member-registration
feature/payment-module
feature/dashboard-kpi
```

Bir branch yalnızca tek geliştirme amacı taşımalıdır.

---

# 5. Bugfix Branch

Hata düzeltmeleri ayrı branch üzerinde yapılmalıdır.

Örnek.

```text
bugfix/login-error
bugfix/payment-rounding
bugfix/report-filter
```

Hata düzeltmeleri geliştirme çalışmalarından ayrılmalıdır.

---

# 6. Hotfix Branch

Canlı ortamda kritik hata oluşursa Hotfix kullanılmalıdır.

Örnek.

```text
hotfix/api-auth
hotfix/database-index
```

Hotfix tamamlandıktan sonra hem `main` hem de `develop` dalına aktarılmalıdır.

---

# 7. Branch Adlandırma

Branch isimleri küçük harf kullanılacak şekilde yazılmalıdır.

Örnek yapı.

```text
feature/
bugfix/
hotfix/
release/
```

Boşluk ve özel karakter kullanılmamalıdır.

---

# 8. Commit Standartları

Commit mesajları açıklayıcı olmalıdır.

Örnek.

```text
feat: add member registration workflow

fix: correct payment validation

refactor: optimize reservation service
```

Belirsiz ifadeler kullanılmamalıdır.

---

# 9. Pull Request

Kod doğrudan ana dallara gönderilmemelidir.

Standart süreç.

```text
Feature
↓
Pull Request
↓
Code Review
↓
Merge
```

Kod incelemesi tamamlanmadan birleştirme yapılmamalıdır.

---

# 10. Merge Politikası

Merge sırasında.

- Çatışmalar çözülmelidir.
- Testler başarılı olmalıdır.
- Kod incelemesi tamamlanmalıdır.

Başarısız test bulunan kod birleştirilmemelidir.

---

# 11. Tag Kullanımı

Canlı sürümler Git Tag ile işaretlenmelidir.

Örnek.

```text
v1.0.0
v1.1.0
v2.0.0
```

Tag'ler değiştirilememelidir.

---

# 12. Korumalı Branch

Aşağıdaki branch'ler koruma altında olmalıdır.

```text
main
develop
```

Kurallar.

- Doğrudan Push yasak.
- Pull Request zorunlu.
- Review zorunlu.

Koruma ayarları Git platformunda etkinleştirilmelidir.

---

# 13. Audit ve Geçmiş

Git geçmişi korunmalıdır.

Kurallar.

- Commit geçmişi gereksiz yeniden yazılmamalıdır.
- Yayınlanmış commit'ler değiştirilmemelidir.
- Kritik Merge işlemleri izlenebilmelidir.

Sürüm geçmişi güvenilir olmalıdır.

---

# 14. Dokümantasyon

Git süreçleri aşağıdaki bilgileri içermelidir.

- Branch yapısı
- Commit kuralları
- Merge süreci
- Release politikası
- Kod inceleme kuralları

Yeni ekip üyeleri aynı süreci takip edebilmelidir.

---

# 15. Genel Kurallar

Git ve Branch yönetimi, Antrenova projesinin sürdürülebilir geliştirme sürecinin temelidir. Tüm geliştirmeler ayrı Feature Branch'lerde yapılmalı, kodlar Pull Request üzerinden incelenmeli, korumalı branch politikaları uygulanmalı ve sürüm geçmişi güvenilir şekilde korunmalıdır.

Bu sayede ekip çalışması kolaylaşır, kod kalitesi artar, yayın süreçleri güvenli hale gelir ve proje büyüdükçe yönetilebilir bir geliştirme altyapısı korunur.
