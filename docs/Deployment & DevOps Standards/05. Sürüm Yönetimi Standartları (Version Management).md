# 05. Sürüm Yönetimi Standartları (Version Management)

> **Doküman Kodu:** DEVOPS-05  
> **Dosya Adı:** `05_VERSION_MANAGEMENT.md`  
> **Versiyon:** 1.0  
> **Durum:** Onaylandı  
> **Bağımlı Dokümanlar:** Git & Branch Strategy, CI/CD Standards, Deployment Principles, Release Management

---

# 1. Amaç

Bu dokümanın amacı, Antrenova platformunda kullanılacak sürüm (Version) yönetimi standartlarını belirlemek ve yazılımın gelişim sürecinin kontrollü, izlenebilir ve geriye dönük takip edilebilir olmasını sağlamaktır.

Sürüm yönetimi yalnızca versiyon numarası vermekten ibaret değildir. Yeni özelliklerin, hata düzeltmelerinin, güvenlik güncellemelerinin ve mimari değişikliklerin düzenli olarak sınıflandırılması ve yayın geçmişinin korunması için temel bir süreçtir.

Platform genelindeki tüm yayınlar bu standartlara göre sürümlendirilmelidir.

---

# 2. Temel İlkeler

Sürüm yönetimi aşağıdaki prensiplere uygun olmalıdır.

- Tutarlı olmalıdır.
- Anlaşılır olmalıdır.
- Geriye dönük takip edilebilir olmalıdır.
- Yayın geçmişini korumalıdır.
- Otomasyonla uyumlu olmalıdır.

Her yayın benzersiz bir sürüm numarasına sahip olmalıdır.

---

# 3. Semantic Versioning

Platform Semantic Versioning (SemVer) standardını kullanmalıdır.

Biçim.

```text
MAJOR.MINOR.PATCH
```

Örneğin.

```text
1.0.0
1.2.4
2.0.0
```

Sürüm numaraları rastgele verilmemelidir.

---

# 4. MAJOR Sürüm

MAJOR sürüm aşağıdaki durumlarda artırılmalıdır.

- Geriye uyumsuz değişiklikler
- Büyük mimari değişiklikler
- API kırıcı güncellemeler
- Büyük ürün sürümleri

Örnek.

```text
1.x.x → 2.0.0
```

---

# 5. MINOR Sürüm

MINOR sürüm aşağıdaki durumlarda artırılmalıdır.

- Yeni özellikler
- Yeni modüller
- Geriye uyumlu geliştirmeler

Örnek.

```text
1.4.0 → 1.5.0
```

---

# 6. PATCH Sürüm

PATCH sürümü aşağıdaki durumlarda artırılmalıdır.

- Hata düzeltmeleri
- Performans iyileştirmeleri
- Güvenlik yamaları

Örnek.

```text
1.5.2 → 1.5.3
```

---

# 7. Release Candidate

Büyük sürümler öncesinde isteğe bağlı olarak RC kullanılabilir.

Örnek.

```text
2.0.0-rc.1
2.0.0-rc.2
```

RC sürümleri Production için varsayılan sürüm olmamalıdır.

---

# 8. Git Tag

Her Production sürümü Git Tag ile işaretlenmelidir.

Örneğin.

```text
v1.0.0
v1.1.0
v2.0.0
```

Tag'ler değiştirilememelidir.

---

# 9. Release Notes

Her sürüm için Release Notes hazırlanmalıdır.

İçerik.

- Yeni özellikler
- Düzeltilen hatalar
- Güvenlik güncellemeleri
- Bilinen sorunlar

Yayın geçmişi herkes tarafından incelenebilmelidir.

---

# 10. Build Numarası

İsteğe bağlı olarak Build numarası tutulabilir.

Örnek.

```text
1.5.0+231
```

Build numarası teknik takip amacıyla kullanılmalıdır.

---

# 11. Geri Dönüş

Her sürüm gerektiğinde önceki sürüme döndürülebilmelidir.

Rollback sırasında.

- Veritabanı durumu
- Migration
- API uyumluluğu

kontrol edilmelidir.

---

# 12. Dokümantasyon

Her sürüm aşağıdaki bilgilerle belgelenmelidir.

- Versiyon
- Yayın tarihi
- Commit bilgisi
- Yayınlayan kişi
- Release Notes

Dokümantasyon güncel tutulmalıdır.

---

# 13. Audit

Sürüm değişiklikleri Audit sisteminde kayıt altına alınmalıdır.

Örneğin.

- Yayın zamanı
- Ortam
- Commit
- Sürüm numarası

Geçmiş sürümler silinmemelidir.

---

# 14. Sürekli İyileştirme

Sürüm yönetimi düzenli olarak gözden geçirilmelidir.

İyileştirilebilecek alanlar.

- Yayın sıklığı
- Geri dönüş süresi
- Release Notes kalitesi
- Otomatik sürümleme

Süreç ekip büyüdükçe geliştirilebilir olmalıdır.

---

# 15. Genel Kurallar

Sürüm yönetimi standartları, Antrenova platformunun düzenli, güvenilir ve izlenebilir şekilde gelişmesini sağlayan temel DevOps süreçlerinden biridir. Tüm yayınlar Semantic Versioning kurallarına göre numaralandırılmalı, Git Tag ile işaretlenmeli, Release Notes hazırlanmalı ve gerektiğinde güvenli şekilde geri alınabilmelidir.

Bu sayede sürüm geçmişi korunur, ekip içi koordinasyon kolaylaşır, kullanıcılar yapılan değişiklikleri takip edebilir ve platform uzun vadede sürdürülebilir bir yayın yönetimi altyapısına sahip olur.
